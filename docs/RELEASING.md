# Releasing mint

mint ships to **three registries** from a single git tag: crates.io (source), PyPI (maturin wheel), npm (cargo-dist installer). All three are **tag-activated**: `git tag X.Y.Z` (or `vX.Y.Z`) + `git push origin X.Y.Z` triggers `release.yml`, and the two registry workflows start only after that run **succeeds** (`workflow_run`, #505). Regular pushes to `master` only run the CI gate (`.github/workflows/ci.yml`).

Pre-release versions (`0.5.0-alpha.1` style) are **skipped** by all three registries: crates.io/PyPI via the `gate` job (`is_stable=false` from `scripts/release-gate.sh`), npm via dist's `publish-prereleases` (unset → default `false`, and `publish-npm`/`publish-npm-github` carry that guard). The GitHub Release still gets the prerelease. Stable releases publish to all three.

## 1. Configure secrets (one-time)

### GitHub

Repo → **Settings → Secrets and variables → Actions → New repository secret**:

| Secret | Source | Purpose |
|---|---|---|
| `CODECOV_TOKEN` | [codecov.io](https://codecov.io) → login → Add repository → copy token | coverage upload + badge |

npm publishing uses **OIDC trusted publishing** (no `NPM_TOKEN` secret): npmjs.com → package `mint-faa` → **Settings → Trusted Publisher → GitHub Actions**, owner `yanqd0`, repository `mint`, workflow `release.yml`.

### crates.io

1. Terminal: `cargo login` → open the URL → paste the API token (generates `~/.cargo/credentials`).
2. Create a second token for CI: crates.io → **Account settings → API Tokens → New token**.
3. GitHub → **Settings → Environments → New environment `crates-io`**:
   - Add `CARGO_REGISTRY_TOKEN` secret (the token from step 2).
   - Add yourself as **Required reviewers** (manual approval gate before publish).

### PyPI

Recommended: **trusted publishing (OIDC, no token)**.

1. PyPI → **Account settings → Publishing → Add a new pending publisher**:
   - Owner: `yanqd0`, Repository: `yanqd0/mint`, Workflow: `publish-pypi.yml`, Environment: `pypi`.
2. GitHub → **Settings → Environments → New environment `pypi`** (matching the name above).

> Alternative: set `PYPI_API_TOKEN` in the `pypi` environment and switch the publish step to `maturin publish`.

## 2. Release flow (per version)

```sh
# 1. Bump version (Cargo.toml is the single source of truth)
#    e.g. edit version = "1.0.0"  (also update plugin.json/marketplace.json for formal releases)

# 2. Commit + tag + push (you, manually)
git add Cargo.toml Cargo.lock claude-plugin/ && git commit -m "chore(release): 1.0.0"
git tag 1.0.0                # 不带 v 前缀（v1.0.0 亦可，两种均触发）
git push origin 1.0.0        # ← the only remote gesture; triggers release.yml (registries follow on success)
```

3. Watch GitHub Actions — the order below is enforced, not a convention:
   - `release.yml` (cargo-dist, tag-triggered) → GitHub Release + npm publish (both reversible).
   - When that run completes **successfully**, `workflow_run` starts the irreversible registries: `publish-crates-io.yml` (approve the `crates-io` environment) and `publish-pypi.yml` (OIDC publish, no approval with trusted publishing).
   - A failed `release.yml` therefore leaves all three registries unpublished — no half-release. Fix the cause and re-run (§4); every publish step is idempotent.

## 3. Verify

```sh
cargo install mint-faa && mint --version
pip install mint-faa && mint --version
npm install -g mint-faa && mint --version
```

For npm also exercise the cold-start concurrency path (three concurrent `mint -V` on a fresh, script-blocked install) — see **Notes → npm installer patch (#504)**.

## 4. Re-running and manual publish

- **A publish step failed** (expired token, flaky network): re-run it from the Actions UI (*Re-run failed jobs*) or `gh run rerun <id> --failed`. Every publish step is idempotent (#507): an already-published version is skipped instead of failing (`crates.io` API probe, `npm view`, PyPI `skip-existing`).
- **A re-run of `release.yml`** re-drives both registry workflows when GitHub emits a new `workflow_run` completion event. If it does not, use the manual entry below.
- **A tag predates these workflows** — dispatch with an explicit tag. The `tag` input is required and is validated against `Cargo.toml` at that tag's commit; the registry workflows accept no branch refs:

  ```sh
  gh workflow run publish-crates-io.yml -f tag=0.9.0
  gh workflow run publish-pypi.yml -f tag=0.9.0
  ```

- Both registry workflows trigger on `workflow_run`, and GitHub only ever fires that from the workflow file that exists on the **default branch** — land workflow changes on the default branch *before* pushing the tag (same rule as the workflow-scope 403 in Notes).

## Notes

- **npm installer patch (#504)**: the npm package's launcher (`binary-install.js`) is generated by cargo-dist and used to delete/re-create the shared install directory without coordination, so concurrent first runs destroyed each other's install. `release.yml` now unpacks each `*-npm-package.tar.gz`, runs `node scripts/npm/patch-installer.mjs <dir>` (lock + staging + atomic rename) and republishes. The patch is anchor-based: if a cargo-dist upgrade changes the generated file, the publish job fails with the missing anchors — refresh `scripts/npm/fixtures/` and the anchors together (see `scripts/npm/README.md`). The published tarball therefore differs from the dist artifact in that one file (GitHub Packages already rewrote `package.json`), so the artifact's `.sha256` still describes the artifact itself.
- **musl**: Linux release binaries are built against `x86_64-unknown-linux-musl` (static linking, single-file, no glibc dependency). glibc (`clang`/`mold`) is local-development only — see `.cargo/config.local.toml` (git-ignored).
- **Workflow-scope 403 (#509)**: `gh release create --target <sha>` fails with `Resource not accessible by integration` when the tag commit adds or modifies `.github/workflows/**` and those changes are not yet on the default branch — the Actions token carries no `workflow` scope for that diff. The step therefore omits `--target` (for an already-existing tag the parameter is ignored by the API anyway). **Rule: land every workflow change on the default branch *before* pushing the tag.** The 0.8.1 release hit this: `host` failed, so `publish-npm`, `publish-npm-github` and `announce` were all skipped while crates.io/PyPI had already published.
- **`release.yml` is generated** by `cargo-dist` (`dist-workspace.toml` is the config source), but `allow-dirty = ["ci"]` marks CI as hand-maintained: the npm OIDC permissions, the `npm@11` install, the `publish-npm-github` job, the #504 patch step, the npm version-exists skip (#507), the omission of `--target` on `gh release create` (#509) and the removal of `on: pull_request` (#510) are local additions. Never regenerate blindly — re-apply those sections (run `dist generate` and diff) instead. `python3 scripts/check-workflows.py` guards them (also in `scripts/precheck.sh` §8 and the CI `release-scripts` job).
- Version must match between the tag and Cargo.toml; `my-git-tag` validates this.
- Verify the published npm launcher after a stable release: `npm i mint-faa@<version> --ignore-scripts` in a scratch dir, then run three `mint -V` concurrently — all must succeed and `node_modules/mint-faa/node_modules/.bin_real/mint` must be complete (with pnpm 10, build scripts are blocked by default, so first use takes the lazy install path).
